# Организация команд

Правила, общие для **всех** групп команд пакета: как читается путь команды, где живут значения, какие
аргументы действуют на группу, как команда выглядит на CLI и в MCP и как описывается структура группы.

Структура каждой группы описана отдельным файлом в этом же каталоге: [`task.md`](./task.md). Общие
правила в файлах групп не дублируются — только ссылка сюда.

Источник фактов — код `@clapp/common` (контракт и ядро) и этого пакета (плагины команд, `src/lib/`).
Ссылки `file:line` даны, чтобы утверждения проверялись, а не принимались на веру.

---

## 1. Словарь

| термин | что это | пример |
| --- | --- | --- |
| **лончер** | исполняемый файл хоста; в записи команды не участвует | `clapp-ai` |
| **group** | корневой узел группы команд; сам действия не выполняет | `task` |
| **item** | промежуточный узел внутри группы (подсемейство действий) | `task item …` (пока не используется) |
| **action** | листовой узел — выполняет работу | `list`, `add` |
| **путь** | последовательность токенов `group [item] action` — то, что набирает пользователь | `task list` |
| **позиционный аргумент** | значение, читаемое по позиции, без имени | `brief "goal"` |
| **опция** | значение с именем через `--` | `--task formatter-rework` |

## 2. Форма пути: от одного до трёх токенов

```
group --опции
group action --опции
group item action --опции
```

| токенов | форма | когда применяется | живой пример |
| --- | --- | --- | --- |
| 1 | `group --опции` | узел с действием и, возможно, с детьми | `brief`, `npm-info`, `init` (без детей) |
| 2 | `group action --опции` | группа с действиями напрямую | `task list`, `task add` |
| 3 | `group item action --опции` | группа, у которой действия сгруппированы по подсемействам | пока не используется |

**Ограничение ядра (сегодня):** узел с детьми действия не имеет. `createGroup`
(`@clapp/common`, `src/plugin-types/command/service.ts:89-105`) применяет к узлу только `command` и
`label`, а `action` регистрируется лишь листовому узлу (`:113-128`). Поэтому форма «1 токен» пока
возможна только для команды **без** детей, а заглушка `action` в группе (например
`src/plugins/command/task/task.plugin.ts:43`) недостижима — она документирует поведение, а не работает.

**Решение:** узел **может** иметь действие и при наличии детей — это планируемое расширение ядра.
Форма `group --опции` остаётся в системе как допустимая; группы, которым такое действие не нужно, её
не используют. Описание ниже считается целевым, ограничение ядра — временным.

---

## 3. Правило: позиционные токены — только путь, значения — опциями

Позиционные места занимает путь (`group`, `item`, `action`) — структура едина для всех команд группы.
Единственное исключение: у команды, которая не является группой, может быть **одно** обязательное
значение (`brief <goal>`); оно последнее и единственное, и это не путь.

Всё остальное — опции, включая выбор задачи (`--task <task-id>`), выбор пункта (`--item`) и любой
селектор по имени.

Причины (технические, а не стилистические):

1. **Цепочка аргументов ослабляет только последний позиционный.** `relaxFilledArguments`
   (`@clapp/common`, `src/plugins/command-argument/context-arguments/lib.ts:18-40`) снимает `required`
   лишь с последнего позиционного аргумента: снятие с более раннего сдвинуло бы смысл следующих
   (`[project] <name>` прочитал бы первое значение как `project`). Значение, которое заполняет цепочка,
   в середине позиционного списка оставить необязательным нельзя.
2. **Именованные значения один-к-одному ложатся на обе поверхности.** В MCP параметры ресурса идут в
   query URI-шаблона (`register-resources.ts:14-20`), параметры инструмента — в `inputSchema`; и то и
   другое именованное. Позиционные значения пришлось бы сопоставлять с именами вручную.
3. **Необязательные позиционные значения неоднозначны.** `task todo <id>` и `task todo` различаются
   только числом токенов; `--task <id>` читается однозначно и не конфликтует с путём.
4. **Обязательность опции ядро не проверяет.** У `ICommandOption` поле `required` означает «значение
   обязательно, если флаг указан» (`buildCommandOption`, `utils.ts:56-77`), а не «флаг обязателен».
   Обязательная опция проверяется в `action` и возвращается failed-результатом. Значит «обязательный
   аргумент» в карте группы — это всегда проверка команды, а не парсера.

## 4. Словарь имён аргументов

Имена — из реестра `@clapp/common` (`src/types/argument/**`), литералы в плагинах не повторяются:

| константа | значение | смысл |
| --- | --- | --- |
| `PROJECT_ARG` | `project` | проект как область работы (`root` или имя пакета) |
| `PROJECT_NAME_ARG` | `project-name` | имя проекта, без селектора `root` |
| `PROJECT_PATH_ARG` | `project-path` | абсолютный путь корня проекта |
| `TASK_NAME_ARG` | `task-name` | идентификатор задачи в проекте (kebab-case) |

Опция на поверхности соответствует имени из реестра (`--task` → `task-name`); новое имя аргумента
добавляется в реестр вместе с привязкой в таблице цепочки — иначе старт падает с понятной ошибкой.

---

## 5. Общие аргументы группы

«Общие аргументы группы» — это **справочный список в документации**, а не унаследованный набор:
`config` группы ядром не применяется (`createGroup` читает только `command` и `label`), и нужные
опции объявляет каждое действие само. Список нужен, чтобы контракт поверхности был описан в одном
месте и команды группы не расходились в именах.

Следствия:

- пункт «общие аргументы» в карте группы читается как **соглашение документации**, а не как механизм;
  действие, которому опция не нужна, её не объявляет;
- единственное значение, которое реально приходит извне объявления, — `project-path`: его заполняет
  шаг `context-arguments` из контекста `CURRENT_PROJECT_PATH`, и в схеме команды оно показывается
  опциональным, потому что пользователь его не пишет;
- проект — всегда текущий, из контекста: `project` и `project-name` объявляются только теми группами,
  которым действительно нужен выбор проекта; для групп задачного workflow они не объявляются;
- если дублирование объявлений начнёт мешать, возврат к вопросу — через расширение ядра, а не правкой
  документации.

## 6. Как группа ложится на поверхности

| что | CLI | MCP |
| --- | --- | --- |
| путь | `task list` | имя сущности `task/list` (`entity-path.ts:19-23`) |
| `COMMAND_KIND_RESOURCE` | вывод в stdout через форматтер | ресурс `clapp://task/list{?…}`, параметры в query |
| `COMMAND_KIND_TOOL` | вывод в stdout через форматтер | инструмент `task/add`, параметры в `inputSchema` |
| группа | контейнер подкоманд | не выставляется (`registry.ts:21-24`) |
| узел с действием и детьми | выполняется без подкоманды | сущность своей поверхности (после расширения ядра) |
| команда без форматтера | ничего не печатает (`clapp.ts:75-78`) | не выставляется, причина в stderr (`registry.ts:31-34`) |

Следствие для системы: **форматтер — часть контракта команды**, а не деталь вывода. Команда без
объявленного формата не существует в MCP. Поэтому в карте группы у каждого листа объявлен и `kind`,
и формат вывода.

## 7. Шаблон описания группы

Каждая группа описывается файлом `<группа>.md` в этом каталоге. Обязательные разделы:

1. **Назначение группы** — 1–3 предложения, что группа делает и для кого.
2. **Состав группы** — таблица `id` / `command` / `parent` / `kind` / поверхность / состояние.
   Состояние — по факту: работает, работает частично (что именно не так), отсутствует.
3. **Общие аргументы группы** — таблица «аргумент / вид / обязательность / кто заполняет / на
   поверхности» и решения: что не объявляется и почему, что приходит из контекста.
4. **Карта узлов** — по схеме ниже.
5. **Правила группы** — то, чего нет в общих правилах: синхронизация состояний, ограничения
   селекторов, особенности записи.
6. **Открытые вопросы** — таблица «# / вопрос / на что влияет»; решённые выносятся в отдельную
   таблицу с решением, чтобы вопрос не открывался заново.

Схема карты узлов — у каждого узла перечислены описание, **общие аргументы** (действуют на узел и всех
его потомков) и **свои аргументы** (только этот узел); для действий отдельно — обязательные и
опциональные:

```
## <action> — <group | item | action> (<KIND>, id: <plugin-id>, command: <segment>)
   description: <одна строка, что делает узел>
   поверхность: <ресурс clapp://…{?…} | инструмент <group>/<action> | нет>

   общие аргументы: <перечень или «—»>
   свои аргументы
     обязательные: <перечень; помнить, что проверяет action — §3>
     опциональные: <перечень или «—»>
   правило: <поведение при разных наборах аргументов; отказ — failed-результат>
```

Правила заполнения карты:

- значения — опциями, позиции заняты путём (§3); обязательность — проверка в `action`;
- у каждого листа объявлены `kind` и формат вывода (иначе в MCP сущности нет, §6);
- проект берётся из контекста; селектор задачи/пункта — опция, а не позиция;
- узел, которого в коде нет, остаётся в карте с состоянием «отсутствует» — карта описывает целевую
  структуру, а не только реализованное;
- уровень `item` вводится только при реальной потребности сгруппировать действия, не «на будущее».

## 8. Чек-лист новой группы

- [ ] файл `<группа>.md` заведён до реализации команды;
- [ ] каждый лист имеет `id`, `command`, `parent`, `kind` и формат вывода;
- [ ] позиционные места заняты только путём; все значения — опциями (§3);
- [ ] обязательные опции проверяются в `action` и дают failed-результат с перечнем допустимых
      значений;
- [ ] проект берётся из контекста, `project`/`project-name` не объявляются без реальной нужды;
- [ ] общие аргументы группы описаны как соглашение документации, а не как механизм ядра (§5);
- [ ] открытые вопросы зафиксированы и решены до реализации; решения записаны в карту;
- [ ] при изменении карты документация правится в том же коммите, что и код.
